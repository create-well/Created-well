## Contract and behavior

- `api/dashboard.ts` exposes the existing `sourceErrors` plus `contentQueryComplete`. The latter says only that this configured CONTENT query's page chain passed the added response-shape/cursor checks. It is not proof of permission scope, a transactionally consistent snapshot, correct source bindings, freshness, or complete visibility of records.
- `api/_notion-sources.ts` rejects malformed CONTENT results, missing or inconsistent flags/cursors, and cursor cycles. Other canonical source query behavior is unchanged. No retries, schedules, writers, public CMS payload, or provider settings are added.
- `snapshotFromDashboard` captures normalized CONTENT rows before forum state is set. It requires the primary source error map, ignores fallback data as source evidence, carries full page IDs, copies/freeze-protects rows, and distinguishes unavailable, partial, genuinely returned empty and available. Unknown or truncated relations remain incomplete; no EVENTS join or identity shortening is used.
- The Moves page renders the new snapshot panel and its existing `retrySync`. A failed CONTENT source visibly identifies the failure without displaying the raw provider error; the last forum state is preserved, while the source panel is unavailable and the overall dashboard is stale. Fallback remains operational but never establishes a source-authority snapshot.
- The context also exposes typed request outcomes for MOVES, PEOPLE, FLOWS, CONTENT and MONEY: `loading`, `failed`, `reported-success`, or `unknown`. `reported-success` means only the server did not report an error for that request. A canonical failure or unknown prevents the global status from being fresh. This does not wire source-specific error states into Home or calendar: they can still imply empty after a source failure and remain a separate queued fix.
- The shared ViewShell stale-banner copy now says data may be stale or incomplete, rather than incorrectly attributing every failure to an old sync. Initial global loading or total transport failure is handled by the existing ViewShell; a named CONTENT failure in an otherwise successful response displays the panel's explicit error and retry. Private access and membership enforcement are not changed.
